# تحليل Instantly وخطة تفوق Jareed Soft

تاريخ المراجعة: 2026-08-23. جرى الاعتماد على صفحات Instantly الرسمية ومركز المساعدة، لا على مواد منسوخة أو ادعاءات غير قابلة للتحقق.

## خريطة نظام Instantly

| الوحدة | ما يقدمه Instantly | قرار Jareed Soft |
|---|---|---|
| Outreach | حملات، تسلسلات، جدولة، تدوير صناديق، A/Z، تحليلات | بناء التسلسلات والتدوير مع فحص جاهزية يمنع الإطلاق الخطر |
| Email Accounts | Gmail/Microsoft/IMAP/SMTP وحسابات جاهزة | إبقاء Gmail وGraph وSMTP وAPI مع تحقق مزود حقيقي |
| Warmup | شبكة Warmup وإعدادات تصاعدية وحسابات مسبقة الإحماء | Ramp-up حقيقي وحدود يومية؛ لا نحاكي تفاعلًا وهميًا أو ندّعي شبكة غير موجودة |
| Deliverability | Inbox placement وDNS وblocklists وspam checker وAI agent | مركز صحة موحد: SPF/DKIM/DMARC، ارتداد، شكاوى، صحة المزود، فحص قبل الإطلاق |
| SuperSearch | قاعدة B2B وإثراء متعدد المزودين وBYOK | ذكاء جامعي: مواقع رسمية، برامج، تقويم، تخصصات، احتياجات، مصادر موثقة |
| Verification | فحص عناوين مقابل Credits | موصلات تحقق متعددة ونتيجة موثقة قبل إدخال العنوان للحملة |
| Unibox | ردود كل الصناديق في واجهة واحدة | صندوق ردود عربي، تصنيف النية، ربط الرد بالجامعة والحملة والخطوة التالية |
| CRM | Leads، Opportunities، Tasks، Calls وSMS | CRM جامعي مبسط: طالب/جامعة/تخصص/احتياج/موعد/حالة فرصة، دون حقول مبيعات مربكة |
| AI Agents | Sales Agent وReply Agent وDeliverability Agent | وكيل جامعة + وكيل حملة + وكيل رد + وكيل سلامة، وكل إجراء عالي المخاطر يحتاج موافقة |
| Automations | نقل leads وsubsequences وwebhooks وZapier/API/MCP | قواعد عربية مرئية: عند الرد/الارتداد/الموعد/تغير التقويم نفّذ إجراءً موثقًا |
| Agency | Workspaces وwhite-label وصلاحيات | مساحات عمل للجامعات/العملاء مع عزل tenant وصلاحيات وتدقيق |

## موضع التفوق

لن ينافس Jareed Instantly كنسخة عامة. التفوق المقصود هو تحويل البحث الجامعي إلى حملة قابلة للقياس في رحلة واحدة:

1. إضافة الجامعة وموقعها الرسمي.
2. بحث موثق في البرامج والتقويم والمواعيد والاحتياجات.
3. استخراج فرص قابلة للتنفيذ مع الجمهور والسبب والمصدر وتاريخ الصلاحية.
4. بناء شريحة من بيانات الموافقة والتخصص والتفاعل.
5. إنشاء رسالة عربية مناسبة للسياق، لا رسالة عامة.
6. فحص الجاهزية من بيانات Backend والمزود فقط.
7. إطلاق تدريجي، ثم تصنيف الرد وربطه بفرصة الجامعة.

## مبادئ الواجهة

- العربية وRTL هي الوضع الأصلي، مع إبقاء أسماء العلامات والبروتوكولات التقنية فقط عند الضرورة.
- عرض «الإجراء التالي» بدل إجبار المستخدم على فهم كل الوحدات.
- أربعة انتقالات للحملة: الجامعة، الرسالة، فحص الجاهزية، الموافقة على الإطلاق.
- الحالات التقنية تُترجم إلى عبارات مفهومة، مع تفاصيل فنية اختيارية.
- لا تعرض الواجهة نجاحًا من طلب HTTP محلي وحده؛ يلزم إقرار مزود أو حدث Backend محفوظ.

## ما نُفذ في هذه المرحلة

- مركز قرار عربي يستمد الأرقام من PostgreSQL.
- توصيات تشغيل مرتبة وفق حالة الصناديق والجمهور والجامعات والبحث والارتداد.
- توزيع الجمهور حسب الجامعة والتخصص ومعدل الرد الحقيقي.
- فحص جاهزية بدرجة 100 مع blockers وwarnings واضحة.
- منع إطلاق الحملة عند صندوق غير متحقق، جمهور فارغ، سعة يومية غير كافية، امتثال ناقص، عنوان غير صالح، أو ارتداد مرتفع.
- تحذير عند غياب المصادر الجامعية أو وجود صياغة تسويقية عالية المخاطر.

## المراحل التالية

1. تسلسلات متعددة الخطوات تتوقف فور الرد أو إلغاء الاشتراك.
2. صندوق ردود موحد مع تصنيف النية وموافقة بشرية قبل الرد الآلي.
3. استخراج «فرص جامعية» منظمة من نتائج البحث مع انتهاء صلاحية المصدر.
4. تحقق البريد وDNS وblocklists عبر مزودات موثقة.
5. موزع يومي متعدد الصناديق يحترم الإحماء والنطاق والمنطقة الزمنية.
6. اختبارات تكامل PostgreSQL/Redis وE2E للواجهة ثم تجربة مزود حقيقية مضبوطة.
